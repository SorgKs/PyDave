# Концепт-документ: Рефакторинг игрового движка

## 1. Архитектурные модули

### 1.1. `anims/obj` (Объекты и Логика)
**Ответственность:** Хранение состояния объекта, поведенческая логика, визуальное представление (спрайт).

*   **Структура данных объекта:**
    *   `id`: Уникальный идентификатор.
    *   `type`: Тип объекта (игрок, враг, платформа, декорация).
    *   `pos`: Логические координаты объекта в мире (x, y).
        *   **Важно:** Точка привязки `(x, y)` зависит от типа движения:
            *   *Наземные (игрок, ходячие враги):* Середина низа спрайта (ноги).
            *   *Летающие/Левитирующие:* Центр спрайта.
            *   *Падающие объекты:* Середина низа спрайта.
    *   `vel`: Текущая скорость (vx, vy).
    *   `size`: Размеры хитбокса (width, height).
    *   `hitbox_offset`: Смещение хитбокса относительно точки привязки `(x, y)`.
        *   Позволяет хитбоксу быть уже спрайта или смещенным вверх/вниз.
        *   Вычисляется как: `hitbox_real_pos = pos + hitbox_offset`.
    *   `sprite_offset`: Смещение спрайта относительно точки привязки `(x, y)`.
        *   Нужно для визуальной коррекции, если точка привязки не совпадает с желаемым местом отрисовки.
        *   Вычисляется как: `draw_pos = pos + sprite_offset`.
    *   `state`: Текущее состояние (idle, run, jump, dead).
    *   `sprite`: Ссылка на текущий кадр спрайта.
    *   `custom_data`: Словарь для специфичных данных (здоровье, таймеры, инвентарь).
    *   `movement_type`: Enum, определяющий правило привязки координат (`GROUND`, `FLYING`, `FLOATING`, `FALLING`).

*   **Функции:**
    *   `init(placeholder)`: 
        *   Инициализация объекта из данных уровня (плейсхолдера).
        *   Настройка `movement_type` для определения точки привязки.
        *   Расчет начальных `hitbox_offset` и `sprite_offset` на основе размеров спрайта и типа движения.
        *   Возвращает имя файла спрайта/анимации для загрузки.
    *   `behave(obj, input, level_triggers)`: 
        *   Обновление логики. Обработка ввода, принятие решений (ИИ), смена состояния.
        *   Изменяет `vel` и `state`, но **не меняет** `pos` напрямую (это делает физика).
    *   `get_sprite(obj)`: Возвращает текущий спрайт для рендерера на основе состояния.
    *   `get_draw_position(obj)`: Вспомогательная функция, возвращающая экранные координаты для отрисовки с учетом `sprite_offset`.
    *   `get_hitbox_bounds(obj)`: Вспомогательная функция, возвращающая реальные координаты хитбокса с учетом `hitbox_offset`.

### 1.2. `physics` (Физика и Коллизии)
**Ответственность:** Универсальный расчет движения, разрешение коллизий со статикой и между объектами.

*   **Входные данные:**
    *   `objects`: Список всех динамических объектов.
    *   `collision_map`: Отдельная тайловая карта проходимости (0 - пусто, 1 - стена, 2 - платформа).
    *   `spatial_grid`: Пространственная сетка (uniform grid) для ускорения поиска пар.
*   **Логика (Два прохода):**
    *   **Проход 1: Индивидуальная физика и статика**
        *   Для каждого объекта:
            *   Применяет гравитацию и трение.
            *   Интегрирует скорость в позицию (`pos += vel`).
            *   Рассчитывает реальные границы хитбокса с учетом `hitbox_offset`.
            *   Проверяет коллизии с `collision_map`.
            *   Разрешает коллизии со статикой (сдвиг `pos`, коррекция `vel`).
            *   **Регистрирует** потенциальные межобъектные пересечения (AABB vs AABB), но не разрешает их.
            *   Записывает информацию о коллизиях со статикой в `obj.collisions`.
    *   **Проход 2: Разрешение межобъектных коллизий**
        *   Построение/Обновление `spatial_grid` на основе новых позиций объектов.
        *   Для каждого объекта поиск соседей в ячейках сетки.
        *   Фильтрация пар через `collision_layers` (битовые маски): например, "игрок" не сталкивается с "другом", "пуля" только с "целями".
        *   Для прошедших фильтрацию пар:
            *   Вычисляет нормаль столкновения, глубину проникновения и точку контакта.
            *   Разрешает столкновение (разлепляет объекты, корректирует скорости).
            *   Добавляет запись в `obj.collisions` для обоих объектов.
*   **Структура записи в `obj.collisions`:**
    *   `target`: Ссылка на объект или ID тайла, с которым произошло столкновение.
    *   `normal`: Вектор нормали столкновения (nx, ny).
    *   `depth`: Глубина проникновения (float).
    *   `point`: Точка контакта (x, y).
    *   `type`: Тип коллизии (`'static_wall'`, `'static_platform'`, `'dynamic'`).
*   **Выходные данные:**
    *   Обновленные объекты с новыми `pos`, `vel`.
    *   Заполненный список `obj.collisions` у каждого объекта, участвовавшего в столкновении.

### 1.3. `anims/obj` (Трансформация)
**Ответственность:** Реакция объекта на произошедшие коллизии.

*   **Функция `transform(obj)`:**
    *   **Условие вызова:** Вызывается для каждого объекта, у которого `len(obj.collisions) > 0`.
    *   **Логика:**
        *   Анализирует список `collisions`.
        *   В зависимости от типа столкнувшегося объекта (`target.type`) и параметров коллизии (`normal`, `point`):
            *   Наносит урон (если `target` враг/шип).
            *   Подбирает предмет (если `target` монета/бонус).
            *   Активирует триггер.
            *   Меняет состояние (например, `state = 'hurt'` при ударе сбоку).
            *   Корректирует поведение (отскок, смена направления ИИ).
    *   **Важно:** Эта функция не меняет `pos` напрямую (физика уже завершилась), но может менять `vel`, `state`, `custom_data` и флаги.

### 1.3. `render` (Отрисовка)
**Ответственность:** Визуализация состояния мира. Не содержит логики.

*   **Входные данные:**
    *   `tilemap`: Тайловая карта уровня (декор, фон).
    *   `objects`: Список объектов.
    *   `camera`: Параметры камеры (смещение, зум).
*   **Логика:**
    *   Отрисовка видимой части `tilemap`.
    *   Сортировка объектов (например, по Y для псевдо-3D).
    *   **Отрисовка объектов:**
        *   Для каждого объекта вычисляет позицию отрисовки: `final_pos = obj.pos + obj.sprite_offset`.
        *   Рисует спрайт, выравнивая его относительно `final_pos` (учитывая, что `pos` может быть центром или низом).

## 2. Поток данных (Game Loop)

### Этап 1: Инициализация (Startup)
1.  **Загрузка ассетов:**
    *   Загрузка тайлов (имена из конфига уровня).
    *   Загрузка спрайтов объектов:
        *   Читаем плейсхолдеры уровня.
        *   Для каждого типа вызываем `anims/obj.init()`, получаем список необходимых файлов.
        *   Загружаем спрайты в память.
2.  **Построение мира:**
    *   Парсинг файла уровня (`level`).
    *   Генерация `tilemap` (визуальные тайлы).
    *   Генерация `surface_map` (карта коллизий, упрощенная или битовая).
    *   Создание списка объектов через `anims/obj.init()` для каждого плейсхолдера.
        *   Внутри `init` устанавливаются правильные оффсеты в зависимости от типа движения.

### Этап 2: Игровой цикл (Frame)
1.  **Input & Behavior (`anims/obj`):**
    *   Для каждого объекта вызывается `behave()`.
    *   Объект читает ввод (для игрока) или принимает решения (ИИ).
    *   Объект выставляет желаемую скорость (`vel`) и меняет анимацию.
    *   *Проверка триггеров:* Если объект пересекает зону триггера, `behave` может обработать это.
2.  **Physics Pass 1 (`physics`):**
    *   Для каждого объекта:
        *   Применение гравитации/трения.
        *   Интеграция скорости в позицию.
        *   Коллизии со статикой (`surface_map`).
        *   Регистрация межобъектных пересечений.
        *   Запись коллизий со статикой в `obj.collisions`.
3.  **Physics Pass 2 (`physics`):**
    *   Разрешение всех зарегистрированных межобъектных коллизий.
    *   Добавление записей о динамических коллизиях в `obj.collisions`.
4.  **Transform (`anims/obj`):**
    *   Для каждого объекта, у которого `len(obj.collisions) > 0`:
        *   Вызов `transform(obj)`.
        *   Обработка последствий столкновений (урон, подбор, триггеры).
5.  **Render (`render`):**
    *   Очистка экрана.
    *   Отрисовка `tilemap`.
    *   Отрисовка объектов:
        *   Получение спрайта через `get_sprite()`.
        *   Расчет позиции отрисовки через `sprite_offset`.
        *   Отрисовка по рассчитанным координатам.

## 3. Вопросы для обсуждения (Critical Design Decisions)

Прежде чем писать код, нужно согласовать следующие моменты:

### Вопрос 1: Структура `surface_map` для физики
Как именно `physics` будет получать данные о коллизиях?
*   **Вариант А:** Та же тайловая карта, что и для рендера, но с флагами проходимости (solid/non-solid). Просто, но менее гибко для наклонов.
*   **Вариант Б:** Отдельная битовая маска или массив AABB (прямоугольников) для сложных форм.
*   **Вариант В:** Функция-коллбэк `is_solid(x, y)`, которую `physics` вызывает. Это делает физику независимой от структуры данных уровня.
*   *Предложение:* Использовать **Вариант А** для начала (тайловая сетка проходимости), так как это проще всего связать с загрузчиком уровней.

### Вопрос 2: Взаимодействие Объект-Объект
Текущая схема описывает коллизии "Объект vs Статичный Уровень".
*   Как обрабатываются коллизии между двумя динамическими объектами (Игрок vs Враг)?
*   Должен ли модуль `physics` проверять столкновения всех объектов друг с другом (O(N^2) или пространственное разбиение)?
*   Или объекты сами решают это в `behave`?
*   *Предложение:* Вынести проверку "Объект-Объект" в отдельный шаг внутри `physics` или в менеджер коллизий, так как универсальная физика должна знать обо всех твердых телах.

### Вопрос 3: Триггеры и События
Где живут триггеры (зоны, активирующие события)?
*   Это специальные объекты с типом "trigger"? Тогда они будут в списке объектов и обработаются в `behave`.
*   Или это часть `surface_map` (метаданные тайлов)?
*   *Предложение:* Сделать триггеры объектами. У них нет спрайта (или он пустой), нет физической реакции (сквозь них можно ходить), но есть логика в `behave`, которая проверяет вход других объектов в свои координаты.

### Вопрос 4: Интерфейс `init` в `anims/obj`
Как мы передаем параметры инициализации?
*   Плейсхолдер в уровне содержит: `{ type: "enemy", x: 100, y: 200, params: { speed: 5 } }`.
*   Функция `init` должна уметь читать `params` и настраивать объект. Нужно определить формат этих данных.

### Вопрос 5: Камера
Модуль `render` должен знать о камере.
*   Камера — это глобальное состояние или объект?
*   Должна ли физика ограничивать движение камерой (чтобы не уйти за край уровня)?
*   *Предложение:* Камера — это отдельная сущность, которая обновляется после физики (следует за игроком) и передается в `render`.

## 4. Детали реализации смещений (Offsets)

### Типы привязки координат (Anchor Points)
Для унификации работы с объектами вводим перечисление типов привязки:

1.  **GROUND (Наземные):**
    *   Логическая точка `(x, y)`: Середина низа спрайта.
    *   Почему: Удобно для проверки "на земле" (y == высота поверхности).
    *   `hitbox_offset`: Обычно `( -width/2, -height )` (если хитбокс от центра) или `(0, -height)` (если хитбокс от низа).
    *   `sprite_offset`: `(0, 0)` (спрайт рисуется точно от ног).

2.  **CENTER (Летающие/Левитирующие):**
    *   Логическая точка `(x, y)`: Центр спрайта.
    *   Почему: Удобно для вращения и симметричного движения в воздухе.
    *   `hitbox_offset`: `( -width/2, -height/2 )`.
    *   `sprite_offset`: `( -width/2, -height/2 )` (если рендер ожидает верхний левый угол, нужно сместить).

3.  **FALLING (Падающие объекты):**
    *   Логическая точка `(x, y)`: Середина низа спрайта.
    *   Почему: Важно точно знать момент касания земли.
    *   Аналогично `GROUND`.

### Пример расчета в `init`:
```python
def init(type, x, y, sprite_w, sprite_h):
    obj = Object()
    obj.pos = (x, y)
    
    if type == 'player' or type == 'walker':
        obj.anchor = 'GROUND'
        # Хитбокс обычно чуть уже спрайта и стоит на "ногах"
        obj.hitbox_offset = (-sprite_w * 0.4, -sprite_h * 0.9) 
        obj.sprite_offset = (-sprite_w / 2, -sprite_h) # Рендеринг от низа-центра
        
    elif type == 'flyer':
        obj.anchor = 'CENTER'
        obj.hitbox_offset = (-sprite_w / 2, -sprite_h / 2)
        obj.sprite_offset = (-sprite_w / 2, -sprite_h / 2)
        
    return obj
```

## 6. Пример использования нового движка

```python
from engine import objects, physics, render

# 1. Инициализация
surface_grid, ROWS, COLS = build_surface_map(level.MAP)
physics.init_physics(TS, surface_grid, ROWS, COLS)

# 2. Создание игрока
player = objects.create_object('player', spawn_x, spawn_y)
objects.compute_offsets(
    player, 
    sprite_w=48, sprite_h=64, 
    hitbox_w=36, hitbox_h=48, 
    anchor_type=objects.ANCHOR_BOTTOM_CENTER
)
player['layer'] = objects.LAYER_PLAYER
player['has_gravity'] = True

# 3. Создание врага
zombie = objects.create_object('zombie', z_x, z_y)
objects.compute_offsets(
    zombie,
    sprite_w=48, sprite_h=48,
    hitbox_w=16, hitbox_h=36,
    anchor_type=objects.ANCHOR_BOTTOM_CENTER
)
zombie['layer'] = objects.LAYER_ENEMY
zombie['has_gravity'] = True

objects_list = [player, zombie]

# 4. Игровой цикл
while running:
    # A. Поведение
    for obj in objects_list:
        objects.behave(obj, input_state, triggers)
    
    # B. Физика (2 прохода)
    physics.update_physics(objects_list)
    
    # C. Трансформация (реакция на коллизии)
    for obj in objects_list:
        if obj['collisions']:
            objects.transform(obj)
    
    # D. Рендер
    cam_x, cam_y = render.update_camera(
        cam_x, cam_y,
        player['x'], player['y'],
        VW, VH, COLS*TS, ROWS*TS
    )
    render.render_tilemap(view, tilemap, cam_x, cam_y, TS, sprites, VW, VH)
    render.render_objects(view, objects_list, cam_x, cam_y, sprites, objects.get_sprite)
```
